How do we know software works?

We define the expected result. We run the software. We compare the actual result with the expected result. Different checks observe different parts of the system.

Correctness starts with an expected result

A check cannot decide what your product should do. You define that rule. The check then reports whether the software follows the rule.

A deterministic test

The result must match an exact value. Example: an empty task title must return HTTP status 400.

An eval

The result receives a score. Example: an AI answer receives points for accuracy, safety, and format.

Simple rule: Given the title “Ship release”, the backend must create one task with that exact title. The word must makes the expected result clear.

Five checks answer five questions

Use the smallest check that can prove the rule. Use larger checks for connections and user workflows.

Unit testVery fast

Question

Does one small function follow its rule?

validateTitle("") must return an error.

It finds

Incorrect calculations, validation, and state rules. It does not prove that the API or UI works.

Integration testFast

Question

Do connected parts work together?

POST /api/tasks must save a task and return status 201.

It finds

Broken routes, incorrect JSON, and store connection errors. It does not prove the browser workflow.

E2E testSlower

Question

Can a user complete the full workflow?

A browser enters a title, selects Add task, and sees the task.

It finds

Broken buttons, browser errors, API errors, and incorrect visible results.

EvalScored

Question

How well does variable behavior meet quality criteria?

Four cases receive weighted scores. The total must be at least 0.90.

It finds

Quality regressions when one exact answer is not required. Evals are common for AI output.

Smoke testAfter deploy

Question

Did the deployed application start and answer basic requests?

GET /health must return status 200.

It finds

Failed starts, unavailable pages, and broken deployment configuration. It is not a complete test.

Why an eval is different

A normal test often has one exact answer. An eval can accept multiple good answers and measure their quality.

Exact test

The result is pass or fail. This works well for API status codes, totals, IDs, and validation rules.

expected status: 201
actual status:   201
result: PASS

Scored eval

Each criterion adds points. A quality gate decides the minimum acceptable score.

valid title:    0.40
right priority: 0.30
safe output:    0.30
total score:    1.00
Required: 0.90
Important: A high eval score proves only the criteria in the dataset. Add real failure cases, edge cases, and safety cases.

Where checks run in CI/CD

CI checks each change. CD deploys an approved change. A failed required check stops the pipeline.

DeveloperPush code

A pull request starts the CI workflow.

CIUnit

Check small rules first. Stop quickly if one fails.

CIIntegration

Check the backend and store connection.

CIEval and E2E

Check quality scores and user workflows.

CDDeploy

Release only after required checks pass.

CDSmoke

Check the running deployment immediately.

Gate rule: If a required test fails or the eval score is below 0.90, CI returns a failure. The merge or deployment must stop.

Small glossary

These words appear in test tools and CI reports.

Assertion

A comparison between the actual result and the expected result.

Test case

One input, one action, and one expected result.

Fixture

Known data or setup that a check uses.

Quality gate

A rule that stops CI/CD when a required result fails.
