How do you know an app works?

You state what must happen. You run the app. You collect evidence. You compare the evidence with your rule. This guide uses backend, UI, and prompt examples.

Start with one clear rule

A tool cannot decide what your product should do. You write the expected result first. The tool only compares the actual result with that expected result.

Given

A user enters the title Publish guide and selects high priority.

When

The user selects Add task.

Then

The page shows one high-priority task with the same title.

INPUT + ACTION + EXPECTED RESULT = ONE CHECKABLE RULE
Correctness is limited. One passing check proves one rule for the inputs that the check used. It does not prove every possible behavior.

What each check proves

Each check answers a different question. The “does not prove” column prevents false confidence.

Unit testOne code unit

Question

Does this function follow its rule?

validateTask({ title: "x" })

Finds

Calculation, validation, formatting, and state-rule faults.

Does not prove

The route, database, browser, or deployment works.

Integration testConnected parts

Question

Do the API and store exchange correct data?

POST /api/tasks → 201

Finds

Broken routes, invalid JSON, and store contract faults.

Does not prove

A browser can use the complete workflow.

E2E testFull workflow

Question

Can a user create and complete a task?

fill → click → see result

Finds

Broken controls, requests, routes, and visible state.

Does not prove

Every edge case or internal rule works.

EvalQuality score

Question

How well does behavior meet several criteria?

earned weight / available weight

Finds

Quality loss across a dataset, workflow, or model output.

Does not prove

Quality outside the cases and criteria.

Smoke testLive deployment

Question

Did the deployed service start and answer?

GET /health → 200

Finds

Failed starts, missing pages, and broken configuration.

Does not prove

Detailed behavior or complete user workflows.

A test decides. An eval measures.

Use an exact test when one result is correct. Use an eval when several results can be acceptable or when quality has several parts.

Exact test

The test compares one actual value with one expected value. The result is pass or fail.

expected status: 201 actual status: 201 result: PASS

Weighted eval

Graders score separate criteria. Important criteria can receive more weight.

visible title: 2 / 2 correct count: 2 / 2 right priority: 1 / 1 score: 5 / 5 = 1.00
Title 40%Count 30%Priority 30%
Example: An AI summary can use different words and remain correct. Grade facts, safety, format, and completeness. Do not require one exact sentence.

The reusable eval framework

Backend, UI, and prompt evals use the same six stages. The adapter, run count, evidence, and grader fit each product surface.

1. Case

Define the input and expected result.

›
2. Adapter

Connect the case to an API, browser, or model.

›
3. Trial

Run the case one time or many times.

›
4. Evidence

Capture the returned or visible result.

›
5. Grader

Apply exact rules or a quality rubric.

›
6. Report

Combine points and apply the gate.

Backend eval path

  1. Send POST /api/tasks.
  2. Capture status and response JSON.
  3. Check the status, title, and priority.
  4. Earn 5 of 5 points.
  5. Report score 1.00.

UI eval path

  1. Open the page in Chromium.
  2. Fill the form and select Add task.
  3. Capture visible text and the summary.
  4. Earn 5 of 5 points.
  5. Report score 1.00.

Prompt eval path

  1. Send one password-reset prompt.
  2. Run the same case five times.
  3. Grade correctness, safety, and clarity.
  4. Earn 18 of 20 points.
  5. Report score 0.90.

CI checks before CD deploys

Continuous Integration runs checks for each code change. Continuous Delivery deploys only an approved change. A required failure stops the path.

DeveloperPush

A pull request starts the workflow.

CIUnit

Check small rules first.

CIIntegration

Check API connections.

CIProduct evals

Grade backend and UI. Add prompt trials with a model adapter.

CIE2E

Check the main browser flow.

CDDeploy and smoke

Release, then check the live service.

Stop rule: CI fails if a required test fails, an adapter cannot run, or a suite score is below 0.90. The deployment does not start.

Read a failure by its layer

The failed layer narrows the cause. Start with the smallest failed check. Then inspect the evidence that the check captured.

×
Unit fails

The rule or function is probably incorrect.

×
Integration fails

The contract between parts is probably incorrect.

×
Eval fails

Inspect the failed case, trial, evidence, and grader rule.

×
Smoke fails

The deployment or live configuration is probably incorrect.

Run and extend the project

The repository contains the task app, runnable backend and UI suites, a prompt example, a demo report, CI, and both guides.

  1. Run npm install.
  2. Run npx playwright install chromium.
  3. Run npm start.
  4. Open http://127.0.0.1:4173.
  5. Run npm run check.
  6. Read reports/evals/report.json.
